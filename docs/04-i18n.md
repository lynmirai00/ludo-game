# Multi-language support (i18n)

## Supported languages
| Code | Name shown in the switcher | App title |
|---|---|---|
| `en` | English | Ludo |
| `vi` | Tiếng Việt | Cờ cá ngựa |
| `ja` | 日本語 | ルドー |

English is the default and the source of truth: every key must exist in `en.ts` first.
Language names in the switcher are always written in their own language, never translated.

## Which language to show
Pick the first one that applies:
1. The logged-in player's saved `locale` (from `GET /api/me`).
2. The language previously chosen on this device (`localStorage` key `lang`).
3. The first browser language in `navigator.languages` that matches `en`, `vi` or `ja` (compare only the part before `-`, so `ja-JP` → `ja`).
4. `en`.

## Language switcher
- A `<select>` in the top bar, visible on every screen, with a translated `aria-label` (`lang.label`).
- Changing it updates the whole UI **instantly, without a page reload**, including the game log, `<html lang="…">` and `document.title`.
- Save the choice to `localStorage`. If logged in, also call `PUT /api/me/locale`.
- Changing language must never reset or interrupt the current game.

## Implementation
No i18n library and no locale in the URL: the language is client-side state, as described above.

`lib/i18n/index.ts` is pure (no React, no DOM), so it can be tested directly:
- Each locale file exports a default object with nested keys: `export default { game: { roll: 'Roll' } }`.
  `en.ts` is the source of truth; `vi.ts` and `ja.ts` are typed against its key structure so a missing or extra key is a type error.
- `translate(lang, key, params)` looks up a dotted key (`'game.roll'`) and replaces `{name}` placeholders from `params`.
- Missing key in `vi` or `ja` → fall back to `en` and `console.warn` it. Missing in `en` too → return the key itself.
- `detectLanguage({ savedLocale, storage, languages })` implements "Which language to show".
- Plurals: a value can be an object of plural forms, chosen with `Intl.PluralRules(lang)`.
  English needs `one` and `other`; Vietnamese and Japanese only use `other`.
  ```ts
  // en.ts
  bots: { one: '{count} bot', other: '{count} bots' }
  // vi.ts
  bots: { other: '{count} máy' }
  ```
- Numbers and dates: always format with `Intl.NumberFormat(lang)` / `Intl.DateTimeFormat(lang)`, never by hand.

`lib/i18n/I18nProvider.tsx` ("use client") wraps the app in `app/layout.tsx`:
- Holds the current language in React state; `useI18n()` returns `{ lang, t, setLanguage }`.
  Changing the language re-renders every component that uses `t`, so there is no listener plumbing.
- Detects the language after mount (the server cannot see `localStorage`). Until then it renders nothing
  inside the app shell, so the user never sees text flash in the wrong language.
- On every change it updates `<html lang>`, and it renders the translated `<title>` element itself (React hoists it into `<head>`;
  before detection it renders the English title). Do not set `metadata.title` in `layout.tsx` and do not assign
  `document.title` by hand: Next.js/React re-commit the head and overwrite it.

## Game log: store events, translate when rendering
The game engine (`lib/game.ts`) must not produce text. It emits structured events, for example:
```js
{ type: 'capture', player: 0, victimColor: 2 }
{ type: 'rolled', player: 1, value: 6 }
```
The UI turns each event into text with `t()` at render time. This way, switching language re-renders the whole log in the new language.

**Watch out for English grammar:** "You rolled a 6" works, but "You has no legal move" does not.
Give each event two keys, one for the human player and one for others:
```js
events: {
  noMove: { self: 'You have no legal move.', other: '{player} has no legal move.' },
}
```
Use the same `self` / `other` structure in all three languages, even where the text is similar.

## API and server
- The server never sends translated text. Errors are `{ "error": { "code": "FORBIDDEN" } }`; the browser shows `t('errors.FORBIDDEN')`. Unknown codes show `errors.UNKNOWN`.
- `PUT /api/me/locale` accepts only `en`, `vi`, `ja`; anything else → `400` with code `INVALID_LOCALE`.
- Player names from ZITADEL are shown as-is, never translated.

## ZITADEL login page language
- Pass `ui_locales` when redirecting to login. ZITADEL has no Vietnamese login page, so for `vi` send `'vi en'`
  (OIDC allows a space-separated preference list):
  `signinRedirect({ extraQueryParams: { ui_locales: lang === 'vi' ? 'vi en' : lang } })`.
- Checked on 2026-10-05 with ZITADEL v4.19.4 (built-in login UI): `ui_locales_supported` in
  `/.well-known/openid-configuration` includes `en` and `ja` but **not `vi`**. With only `ui_locales=vi` the login page
  falls back to the browser's language if supported (a Japanese browser shows Japanese), otherwise English;
  `'vi en'` makes Vietnamese players consistently see English. Custom login texts only exist for supported
  languages, so they cannot add Vietnamese. Note this in the README.

## Fonts and layout
- Use a font stack that covers Vietnamese diacritics and Japanese characters. Example:
  `font-family: system-ui, "Segoe UI", "Hiragino Sans", "Yu Gothic UI", "Noto Sans JP", sans-serif;`
  and a `:lang(ja)` rule that puts the Japanese fonts first.
- Also add a `:lang(vi)` rule that puts fonts with full Vietnamese coverage first, e.g.
  `"Segoe UI", "Helvetica Neue", Arial, "Noto Sans", system-ui, sans-serif`. On Japanese Windows, `system-ui`
  resolves to Yu Gothic UI, which renders stacked diacritics wrongly ("Tiếng" shows as "Tiê ́ng").
  Language options in the switcher get their own `lang` attribute so each name uses the right fonts.
- Buttons and labels must fit the longest translation. Vietnamese is often the longest of the three; Japanese is usually the shortest but taller. Never set fixed widths on text elements.

## Tests (`test/i18n.test.ts`)
- Every key in `en.ts` exists in `vi.ts` and `ja.ts`, and the other files have no extra keys.
- No value is an empty string.
- Placeholders match across languages: if `en` has `{player}` and `{value}`, so do `vi` and `ja`.
- Every plural object has an `other` form; English plural objects also have `one`.
- `t()` falls back to English for a missing key and returns the key itself if English is missing too.
- Language detection follows the order above (test with fake `navigator.languages` and storage).
- Scan `app/` and `components/` (`.tsx` files) for hardcoded user-facing text (a simple regex check is fine):
  no literal text between JSX tags, and no string literals in `aria-label`, `title`, `alt` or `placeholder` props.
  Language names in the switcher come from a constant, not from JSX text. Check that the scan really catches a planted example.
